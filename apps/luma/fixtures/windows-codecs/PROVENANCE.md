# Windows-codec test inputs

Everything here is generated by Luma's own scripts from colour arithmetic. There is no camera
file, no third-party image and no content with a licence of its own. A colour pattern stands in
for a photo so that every flip and rotation can be read from the pixels.

The picture: four quadrants, clockwise from top-left red (230, 30, 30), green (30, 200, 60),
yellow (240, 220, 40), blue (40, 70, 230), with a white diagonal tick in the top-left 12 pixels
(`examples/make_wic_fixtures.rs`; the DNG uses the same colours as a 16-bit linear scene).

| File | How it was made | Used to prove |
| --- | --- | --- |
| `pattern.heic` | The Windows HEIF encoder (HEIF Image Extensions 1.2.48) through WIC, 96 x 64 | HEIC decodes; colours land in the right quadrants |
| `irot1.heic` `irot2.heic` `irot3.heic` | `pattern.heic` plus an `irot` property (anticlockwise quarter turns 1, 2, 3) added by `scripts/heic_transform.py`, which rewrites only `meta` and shifts `iloc` offsets | The Windows decoder applies container rotation; Luma does not turn it twice |
| `imir0.heic` `imir1.heic` | the same, with an `imir` property of value 0 or 1 | The decoder applies container mirroring: value 0 exchanges top and bottom, value 1 left and right (observed in the pixels; matches ISO/IEC 23008-12:2022 as quoted by libavif's `avifImageMirror`) |
| `irot1-imir0.heic` | both properties, rotation first | Order of transforms (rotation, then mirror) |
| `pattern.jxr` | The built-in Windows JPEG XR encoder through WIC, 96 x 64 | JPEG XR decodes |
| `synthetic-cfa.dng` | `scripts/make_dng.py`: a valid DNG 1.4 Bayer (RGGB) 16-bit mosaic of the same scene, linear sRGB colour matrix, small EXIF block (make, model, ISO 200, 1/125 s, f/2.8, 24 mm, date) | A DNG container decodes (on the development machine through Microsoft's Raw Image Decoder); EXIF is read from its IFDs |
| `synthetic-cfa-orient6.dng` | the same with EXIF orientation 6 | That decoder returns stored orientation, so Luma turns it upright (not done for any other decoder or for non-DNG RAW) |
| `truncated.heic` | the first 60% of `pattern.heic` | A damaged HEIC fails with a message, not a crash |
| `garbage.dng` | a TIFF-looking header followed by text | A file that is not a DNG fails with a message naming DNG |
| `oversize-side.jxr` | WIC JPEG XR encoder, 17000 x 16 | Rejected on the per-side limit before any pixel is copied |
| `oversize-pixels.jxr` | WIC JPEG XR encoder, 6000 x 5000 (30 MP) | Rejected on the pixel budget before any pixel is copied |

The synthetic DNG proves that the Raw Image Decoder Windows chose here reads a real DNG container
and that Luma's orientation and EXIF handling work for it. It proves nothing about any other
decoder (including the built-in DNG decoder, which was not the one chosen) or any camera model: no
camera RAW sample (CR2, CR3, NEF, ARW, ...) is available in this repository.

Regenerate with:

```powershell
cargo run --release --example make_wic_fixtures -- <folder>          # HEIC and JPEG XR via WIC
python -I scripts/make_dng.py <folder>/synthetic-cfa.dng
python -I scripts/make_dng.py <folder>/synthetic-cfa-orient6.dng --orientation 6
python -I scripts/heic_transform.py pattern.heic irot1.heic --irot 1   # and the others
```

The Windows HEIF encoder's output is not byte-identical from run to run, so these files are kept
as generated rather than regenerated on every build. Hashes are in `SHA256SUMS`.
